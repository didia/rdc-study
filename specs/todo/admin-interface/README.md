**Status:** Proposed · **Owner:** Aristote · **Date:** 2026-10-06

(1) track and work **service requests** (replacing the Excel tracker "Tracking des conversions demande assistance")
and (2) reach the existing **content** tooling from one place.

## Why this exists (what the spreadsheet tells us)

The workbook has one tab per pipeline state (En cours, Contacté, Relancé, En discussion, En attente du client,
Va passer au bureau, En attente de paiement, Acompte payé, Échec, Sans suite), plus lookup tabs (Service,
Pays de destination, Pays d'origine) and a Journal tab. Facts from analysing it:

- **595 requests from 555 distinct people**, July 2022 → June 2024. Every request appears on exactly one tab, so
  *the tab a row lives on is its status*. Moving a row between tabs = copy/paste by hand.
- Only ~130 rows carry an explicit "Etat actuel" value; the rest are only "in En cours" (i.e. untouched).
- Data quality is poor and is the main argument for a real database: country spellings
  (`Congo-Kinshasa` / `congo-kinshasa` / `Guinee`), status typos (`En discution avec Mm Nadia`),
  shifted columns on some tabs (a phone number in the "Pays d'origine" column, a package slug in the country column),
  and the "Litiges" column mostly holding a *copy of the request message*.
- The request message ("Je suis X, originaire de Y. Je veux une assistance pour admission au Canada. Mon numéro
  WhatsApp est …") is machine-generated by the site form, so it can be **parsed back into structured fields** on import
  and **sent as structured fields** going forward.
- The only follow-up channel is WhatsApp, handled by one person; there is no reminder system, no ownership, no
  payment record, and no history beyond a hand-kept Journal tab.
- The tracker is named "conversions": the real business question is *how many requests turn into a paid
  engagement, and where do we lose them?* — that drives Phase 2.

## Phasing at a glance

Every phase ships something the team can use on its own the day it merges.

| Phase | Outcome for the team | Rough size |
|-------|----------------------|------------|
| **1 — Pipeline tracker** | Stop using Excel. New website requests land in the console automatically; staff list/search/filter requests, change status, add notes, assign owners; full history kept; legacy 595 rows imported. | Large (split into 3 PRs, see phase doc) |
| **2 — Daily operations** | Know what to do today: "to follow up" queue with due dates, kanban board, conversion dashboard, WhatsApp message templates, CSV export, duplicate merge. | Medium |
| **3 — Payments & documents** | Record deposits/balances (Mobile Money, cash at the office), attach contracts/receipts/client documents, track delivery after payment, revenue reports. | Medium |
| **4 — Content & hardening** | One sign-in story (CMS off deprecated Netlify Identity), content shortcuts/draft overview, email notifications, retention & data-subject tooling, e2e tests, backup drill. | Medium |

Phase 1 is deliberately the heaviest: a tracker that cannot receive live requests goes stale in a week, so
intake, auth and import all have to ship together.

## Out of scope (for all four phases)

- A client-facing portal or client login (clients are contacted on WhatsApp/email as today).
- Moving articles/guides/scholarships into the database — content stays Markdown-in-git (see decision doc §4).
- Online payment processing (payments are Mobile Money / cash today; we only *record* them).
- A built-in WhatsApp API integration (Phase 2 uses `wa.me` deep links + templates; API is a later option).

## Open questions (defaults chosen so work is not blocked)

| # | Question | Default assumed in the specs |
|---|----------|------------------------------|
| 1 | Who needs access and with what rights? | Roles `admin` (Aristote), `agent` (e.g. the WhatsApp follow-up person), `mentor` (Phase 3, sees only assigned requests), `viewer`. |
| 2 | What was the "Litiges" (disputes) column for? | Data suggests it was unused/mis-filled. Model a simple `has_dispute` flag + note event; do not import its content. |
| 3 | Currency and amounts | USD. Prices come from `data/services/*.md`; real amounts are typed per payment (the form doc mentions 200 $ in two 100 $ tranches while `assistance.md` says 300). |
| 4 | Retention of personal data | Keep 24 months after a request is closed, then anonymise (Phase 4). Confirm with whatever the privacy policy promises. |
| 5 | Should "information"-only visitors be tracked? | Today they only go to the newsletter. Phase 1 logs them as lightweight `information` requests behind a flag so the funnel top is measurable. Can be switched off. |
| 6 | Legacy services (`vente-billet`, `refus-permis`, `projet-etudes`, `analyse-permis-etudes`) | Kept as selectable service types for manual entry; not offered on the site form. |
| 7 | Netlify plan | Not needed for the recommended path (Supabase). Required only if Netlify Database were chosen (credit-based plans). |
