# RDC Etudes Admin Interface — Overview

**Status:** Proposed · **Owner:** Aristote · **Date:** 2026-10-06

Build a private admin console, served from the rdcetudes.com Next.js app, that lets the RDC Etudes team
(1) track and work **service requests** (replacing the Excel tracker "Tracking des conversions demande assistance")
and (2) reach the existing **content** tooling from one place.

## Decisions already made by the owner

| Decision | Consequence in the specs |
|----------|--------------------------|
| **Clean start — the old tracker's history is not imported.** | No import script, no `legacy_*` columns or sources. The workbook is archived read-only outside the repo and the console starts empty. |
| **Assistance costs 400 $ (admission, CAQ, équivalence) and 600 $ (visa); prices must be editable from the admin (they will change).** | Prices move into the database (`service_prices`, keyed by service **and package scope** so visa can differ from the rest) and are edited at `/admin/tarifs`; the public site (service cards show "dès 400 $"; the assistance form shows the exact price for the chosen package) reads them from there, and each request stores the price quoted at submission. `data/services/assistance.md` is set to 400 now (the default); the duplicated price constants are removed in Phase 1 ([phase 1 §1C](./phase-1-pipeline-tracker.md#pricing-editable-from-the-admin)). |
| **Personal data will be stored in the database.** | The privacy/security controls (RLS, MFA, audit trail, retention, privacy-policy update — [00 §5](./00-decision-and-architecture.md), [phase 4](./phase-4-content-and-hardening.md)) are required, not optional. |

## Why this exists (what the old Excel tracker tells us)

The workbook ("Tracking des conversions demande assistance") has one tab per pipeline state (En cours, Contacté,
Relancé, En discussion, En attente du client, Va passer au bureau, En attente de paiement, Acompte payé, Échec, Sans
suite), lookup tabs (Service, Pays de destination, Pays d'origine) and an unused Journal tab. We do not import it, but it
defines the process the console must support:

- *The tab a row lives on is its status*; moving a lead = copy/paste by hand. The console models the same stages as a status
  field with an automatic history.
- Free-text countries and statuses (`Congo-Kinshasa` / `congo-kinshasa` / `Guinee`, `En discution avec Mm Nadia`) and
  shifted columns show why vocabularies are controlled lists and why structured data must be captured at the source.
- The request message ("Je suis X, originaire de Y. Je veux une assistance pour admission au Canada. Mon numéro
  WhatsApp est …") is generated by the site form from structured answers, so intake sends those fields directly.
- The only follow-up channel is WhatsApp, handled by one person; there is no reminder system, ownership, payment record or
  history beyond a hand-kept Journal tab.
- It is named "conversions": the real business question is *how many requests turn into a paid engagement, and where do
  we lose them?* — that drives Phase 2.

## Phasing at a glance

Every phase ships something the team can use on its own the day it merges.

| Phase | Outcome for the team | Rough size |
|-------|----------------------|------------|
| **1 — Pipeline tracker** | Stop using Excel. New website requests land in the console automatically; staff list/search/filter requests, change status, add notes, assign owners; full history kept. Starts empty (clean start). | Large (split into 3 PRs, see phase doc) |
| **2 — Daily operations** | Know what to do today: "to follow up" queue with due dates, kanban board, conversion dashboard, WhatsApp message templates, CSV export, duplicate merge. | Medium |
| **3 — Payments & documents** | Record deposits/balances (Mobile Money, cash at the office), attach contracts/receipts/client documents, track delivery after payment, revenue reports. | Medium |
| **4 — Content & hardening** | One sign-in story (CMS off deprecated Netlify Identity), content shortcuts/draft overview, email notifications, retention & data-subject tooling, e2e tests, backup drill. | Medium |

Phase 1 is deliberately the heaviest: a tracker that cannot receive live requests goes stale in a week, so
intake and auth have to ship together.

## Out of scope (for all four phases)

- A client-facing portal or client login (clients are contacted on WhatsApp/email as today).
- Moving articles/guides/scholarships into the database — content stays Markdown-in-git (see decision doc §4).
- Online payment processing (payments are Mobile Money / cash today; we only *record* them).
- A built-in WhatsApp API integration (Phase 2 uses `wa.me` deep links + templates; API is a later option).

## Open questions (defaults chosen so work is not blocked)

| # | Question | Default assumed in the specs |
|---|----------|------------------------------|
| 1 | Who needs access and with what rights? | Roles `admin` (Aristote), `agent` (e.g. the WhatsApp follow-up person), `mentor` (Phase 3, sees only assigned requests), `viewer`. |
| 2 | What was the old "Litiges" (disputes) column for? | It looked unused. Model a simple `has_dispute` flag + note event. |
| 3 | Deposit rule for the Assistance fee | USD. The old form doc described two equal tranches; Phase 3 uses a configurable deposit share, default 50 % (200 $ of 400 $, or 300 $ of 600 $ for visa). Confirm. |
| 8 | Prices of the other services | Today the site disagrees with itself: service cards read `data/services/*.md` while the form reads a code constant. Assistance = 400 in both now (visa = 600 is new and exists in neither). For the rest, the database is seeded from what the **form** charges (consultation 30, vérification 150, vérification + lettre 200, information free); the `.md` files say vérification 100 and vérification + lettre 150. Confirm the right values; they are editable afterwards anyway. |
| 4 | Retention of personal data | Keep 24 months after a request is closed, then anonymise (Phase 4). Confirm with whatever the privacy policy promises. |
| 5 | Should "information"-only visitors be tracked? | Today they only go to the newsletter. Phase 1 logs them as lightweight `information` requests behind a flag so the funnel top is measurable. Can be switched off. |
| 6 | Service types beyond the site's five (`information`, `assistance`, `consultation`, `verification`, `verification-et-lettre`) | None for now (the old workbook also listed ticket sales, refusal analysis, study-project drafting). Add to `lib/admin/vocab.ts` if those services are still offered. |
| 7 | Netlify plan | Not needed for the recommended path (Supabase). Required only if Netlify Database were chosen (credit-based plans). |
